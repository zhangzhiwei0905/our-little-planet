# 多选手帐上传：完整调试版快捷指令

本配置用于定位“选择 Live Photo 后只上传了静态图片”的问题。
请复制现有快捷指令，改名为「手帐上传调试」，保留原指令。
默认只生成媒体包和调试日志，不发送网络请求，不新增手帐。

先只选一张在系统相册里确认能播放的 Live Photo。
在这张图的日志正确之前，不要用整批旧照片反复上传。
本次配置是诊断方案，不假设增加计数操作就一定能让系统正确识别实况。

## 0. 阅读约定

下面每个表格从上到下就是要添加的真实操作，编号用于找位置。
编号不是输入内容，不需要创建叫 A01、B01 的变量。

文本中的 `[变量名]` 表示在该位置插入蓝色变量：
不要把方括号和变量名一起当作普通文字输入。
例如 `item-[媒体序号]`，实际应是文字 `item-` 后面跟一个蓝色的「媒体序号」变量。

### 变量选择的统一规则

| 使用位置 | 类型 | “获取”字段 |
| --- | --- | --- |
| 原媒体、筛选结果、图片、视频、文件列表、ZIP | 保留自动识别的默认类型 | 完整对象／默认值，不选相簿、宽度、名称等属性 |
| 视频数量、实况数量、编码数量、所选数量、允许上传 | 自动识别为数字；必要时改成数字 | 数字本身／默认值 |
| 调试日志、文件名、扩展名、配对名 | 自动识别为文本 | 文本本身／默认值 |

如果弹窗里只有“相簿、宽度”等属性而你不知道如何恢复完整对象：
清除这个输入变量，重新选择正确操作的魔法变量输出，插入后不再点任何属性。
必要时点「显示操作」确认输出来源。
不要因为看到两个输出都叫「相簿」或「计数」，就假设它们是同一份内容。

日志里的文件名和扩展名通过专门的「获取文件的详细信息」操作读取。
不要为了记日志，去修改原媒体变量本身的“获取”属性。

### 计数与判断的统一规则

所有「计数」都统计「项目」，不是字符、字词、句子或行。
判断数量时使用“数字大于 0”，不是“有任何值”。
所有表格里写明的输入都要手动指定，不能依赖“自动使用上一操作”。

### 设置名称的统一规则

所有媒体的「设置名称」都使用蓝色变量 `配对名`。
不要手打“配对名”，也不要手动把视频改成 `.jpg` 或 `.mov`。
保留自动附加原扩展名的设置；「不包含文件扩展名」保持关闭。

### 两个不同的累计变量

| 变量 | 内容 | 使用方式 |
| --- | --- | --- |
| `上传文件` | 真正的图片／视频文件 | 只用「添加到变量」累计文件；不用文本初始化 |
| `调试日志` | 一行行文字 | A04 初始化，之后用「添加到变量」追加日志文字 |

每个日志点都是独立的「文本」和「添加到变量」两个操作。
不要把日志文字加入 `上传文件`，也不要把照片加入 `调试日志`。

## I. 解包核对：检查 ZIP 真正包含什么

为了不只检查打包前的变量列表，调试版会把刚生成的 ZIP 再解包一次。
这只是读取这个新 ZIP，不删除原照片，不把解包结果替换成上传媒体包。
初次调试只选一张小实况，避免大视频压缩和解压占用过多内存。

| 编号 | 操作 | 输入与设置 |
| --- | --- | --- |
| I01 | 解压缩归档／提取归档（Extract Archive） | 输入明确选变量 `媒体包` |
| I02 | 设定变量 | 名称 `ZIP内文件`；内容选 I01 解包后文件的完整输出 |
| I03 | 计数 | 输入 `ZIP内文件`；统计项目 |
| I04 | 设定变量 | 名称 `ZIP文件数量`；内容选 I03 数字 |
| I05 | 文本 | `[ZIP] before=[待打包数量] after=[ZIP文件数量]` |
| I06 | 添加到变量 | 将 I05 文本加入 `调试日志` |
| I07 | 重复每一项 | 输入 `ZIP内文件`；J 的所有操作放在这个新循环内部 |

这里是第二个循环，不是原来的照片循环。
J01 必须取第二个循环自己的「重复项目」，也就是解包后的文件。

| L07 | 合并文本 | 输入 `调试日志`；分隔符换行 |
| L08 | 设定变量 | 名称 `完整调试文本`；内容选 L07 文字 |
| L09 | 拷贝到剪贴板 | 输入 `完整调试文本` |
| L10 | 快速查看 | 输入 `完整调试文本` |
| L11 | 否则 | K04 的“否则”；进入不上传的调试结束流程 |
| L12 | 快速查看 | 输入 `调试文本` |
| L13 | 停止并输出 | 输出 `调试文本`，确保这里之后没有另外一份上传操作 |
| L14 | 结束如果 | 结束 K04；快捷指令至此完成 |

L03 请求头：

| 名称 | 值 |
| --- | --- |
| `Authorization` | `Bearer ` 后面接现有令牌，中间有一个空格 |

不要手动加 `Content-Type`。请求体选“表单”，不是 JSON：

| 字段名 | 字段类型 | 值 |
| --- | --- | --- |
| `type` | 文本 | `journal` |
| `text` | 文本 | 蓝色变量 `正文` |
| `media` | 文件 | 蓝色变量 `媒体包`，不是 ZIP内文件、调试文本或文件名 |

如果网络动作直接报错停止，K03 保存的上传前日志仍可用于排查。
将错误提示和上传前日志一起反馈，不要发送 Authorization 头。

## 正常的一张实况日志

下面是格式示例，不是固定的设备类型名称。
`inputType` 和 `outputType` 的具体文字以你的手机实际输出为准。
视频扩展名可能是 m4v、mov 或 mp4，不能要求它必须是某一个。

```text
[START] uploadFlag=0
[SELECT] mediaCount=1
[ITEM] index=1 base=item-1 inputType=照片媒体
[VIDEO_MATCH] index=1 count=0
[LIVE_MATCH] index=1 count=1
[BRANCH] index=1 mode=live
[ENCODE] index=1 count=1 outputType=媒体
[LIVE_ADDED] index=1 photo=added video=added base=item-1
[PRE_ZIP] selected=1 files=2
[ZIP] before=2 after=2
[ZIP_FILE] seq=1 name=item-1.jpg ext=jpg type=图像
[ZIP_FILE] seq=2 name=item-1.m4v ext=m4v type=媒体
```

A01 为 0 时，日志不应该出现 `[UPLOAD]` 和 `[HTTP_RESULT]`。
此时不会新增手帐，最后的日志已进入剪贴板。

## 日志读法：哪个位置丢了实况

| 日志现象 | 能确认的事实 | 下一步检查 |
| --- | --- | --- |
| 已确认选实况，`LIVE_MATCH count=0`，接着 `mode=static` | 实况筛选没有得到项目，视频编码分支没执行 | B01 原媒体是否完整；D01 的筛选输入和条件；D02 是否误取相簿属性 |
| `LIVE_MATCH count=1`，但没有 `mode=live` | 筛选得到了项目，但后续分支未按预期进入或执行中断 | D07 是否引用手动数字变量实况数量，并使用大于 0 |
| 有 `mode=live`，在 `[ENCODE]` 前直接报错 | 编码动作没有正常完成 | E07 输入必须为原媒体；查看具体错误；核对仅音频选项 |
| `ENCODE count=0` | 编码没有提供输出项目 | E07 输入、实况是否能在系统相册播放、素材是否可获取 |
| 有编码输出，E27 却显示图片 | 所谓动态输出不符合预期 | E08 是否引用编码操作输出；E21、E22 是否误引用图片重命名输出 |
| E27 能播放，但 `PRE_ZIP files=1` | 视频可用，但累积文件列表不完整 | E06、E23 是否都添加到同一个上传文件变量；E23 是否用了实况视频文件 |
| `PRE_ZIP files=2`，`ZIP after=1` | 文件列表与归档中实际项目数不同 | H05 输入；文件名、扩展名是否重复导致覆盖；两个添加是否其实指向同一文件 |
| ZIP 两个文件都为 jpg | 打包进去的是两份图片，不是图片加视频 | E21、E22、E23 的变量来源，不再改配对名 |
| ZIP 动态扩展名为 m4a、mp3 等音频 | 动态部分实际是音频 | E07 关闭仅音频，重新使用单张已成功的编码配置 |
| ZIP 图片和视频的基底不同 | 两部分不能按同名规则配对 | E04、E21 是否都使用同一个配对名变量，且保留各自的扩展名 |
| ZIP 有同名图片和可播放视频，但服务器仍不显示 LIVE | 手机端已有动态资源，需要继续检查请求和服务器 | L03 必须传原媒体包；反馈完整日志及返回条目 id |

没有 `[ENCODE]` 不能单独证明是哪一项条件错了。
结合 `[VIDEO_MATCH]`、`[LIVE_MATCH]`、`[BRANCH]` 和是否报错一起判断。
日志说明的是实际执行路线，不要仅凭一个图标、一个变量名字断言类型正确。

## 推荐的三轮测试

### 第一轮：只选一张实况，A01 保持 0

预期：

1. `VIDEO_MATCH` 为 0。
2. `LIVE_MATCH` 为 1。
3. 进入 `mode=live`。
4. E27 能播放动态。
5. 待打包数量为 2，ZIP 中确实有一张图片和一个视频。
6. 不出现网络上传日志，不新增手帐。

如果不是这个结果，直接粘贴整段日志即可定位，不要重新上传。

### 第二轮：选择一张静态、一张实况、一个短视频，A01 保持 0

预期：

1. 所选数量为 3。
2. 每项分别进入 static、live、video 分支；顺序以选择结果为准。
3. 待打包数量为 4。
4. ZIP 中有两张图片和两个视频，其中只有实况的两部分同基底。
5. 不新增手帐。

### 第三轮：第一、二轮正确后，把 A01 改成 1

先只上传一张实况，预期接口返回：

```json
{
  "ok": true,
  "type": "journal",
  "mediaCount": 1,
  "path": "/journal"
}
```

真实响应还包含 id 和 date，不应要求它恰好只有上面的字段。
`mediaCount` 是网站最终展示的逻辑媒体数，所以一个实况的两个文件只算 1。
不要在收到成功结果后重复提交同一批；当前 quick 尚无请求级去重。

## 从这份完整调试版复制纯相册指令

不要在手帐实况还没定位成功时同时改第二份，以免两份不同配置互相干扰。
手帐版正常后，复制它，改名「相册上传调试」。

1. 删除 A05 请求输入和 A06 保存正文的动作。
2. L03 表单的 `type` 改为文本 `photo`。
3. 删除 L03 的 `text` 字段，不留一个引用已删除正文的空变量。
4. L01 日志文字改为 `[UPLOAD] mode=photo selected=[所选数量] zipFiles=[ZIP文件数量]`。
5. 其余所有筛选、编码、命名、日志和归档动作保持完整。
6. A01 仍先保持 0，确认日志；允许上传时再改成 1。

相册指令的请求表单：

| 字段名 | 字段类型 | 值 |
| --- | --- | --- |
| `type` | 文本 | `photo` |
| `media` | 文件 | 蓝色变量 `媒体包` |

成功时 `type` 为 photo，`path` 为 `/album`，不创建手帐。
这份调试版会解包核对 ZIP，不适合拿大视频做第一轮测试。
正常流程一次最多 9 项媒体，上传包和解包媒体总量各不超过 500MB，还受手机和线上代理限制。
这套图片加视频用于网站实况回放，不是苹果原始 Live Photo 的无损备份。
